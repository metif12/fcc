fcc

A fast, plugin-able and extendable C compiler written in pure V. Every stage — inputs, outputs, hooks, CLI commands — is an extension behind a registry; the stock compiler ships as default extensions, and Brainfuck and Bash ship as worked examples.

Status

fcc is a working, plugin-able C compiler: it translates whole C programs to x86-64 assembly, assembles that text in-process to machine code, and writes COFF (Windows) and ELF (Linux) objects, with no external assembler involved. It supports both x86-64 ABIs (Microsoft and System V), `_Atomic` integer compound assignment via compare-and-swap, `__asm__` with memory and general-register constraints, a best-effort C→V translator (`--to-v`) and c2v-style V bindings (`--to-v-bindings`). The C front end is validated against three independent oracles; the plugin system is exercised by the Brainfuck and Bash language plugins, config-declared external inputs, and by the CLI/config/build commands that ship with it.

How ready, and what is not cross-compiled

Whole translation units work today: data section with relocations, initializers and bitfields, the full expression and statement walk, variadic calls into mingw’s C library, struct returns of every size, floating point including long double, VLAs, and all 19 standard headers. The 20 differential programs, all 220 c-testsuite cases, and all 20 objtest programs agree with tcc/gcc/GAS. Both x86-64 ABIs emit working objects (Microsoft x64 by default, System V via -target=x86_64-linux); anything else is refused at codegen rather than guessed.

Diagnostics

Errors keep the terse tcc: first line the V driver keys on, followed by a source block with file, line, column, a caret span, and = help: hints where the fix is known:

tcc: foo.c:12:9: expected ";", found "bar"
 --> foo.c:12:9
  |
12 | int x = 5  bar = 6;
  |              ^^^
  |
  = help: a declaration or statement ends with `;` — one is missing before this token

Quick start

Prerequisites: the V toolchain plus a checkout of it (fcc takes its oracle tcc and its linker gcc from there).

$env:VCC_V_ROOT = 'C:\path\to\v'
$env:TMPDIR = "$env:LOCALAPPDATA\Temp\opencode\vccbuild"
v -enable-globals -o fcc.exe .
v -enable-globals test .
fcc plugin list                       # every input, output, hook and command
$env:VCC_PROBE_DIR = "$env:LOCALAPPDATA\Temp\opencode\va-probe"
v -enable-globals run tools/probe/probe.v     # differential programs vs tcc/gcc
v -enable-globals run tools/objtest/objtest.v # native -c vs as: bytes and linked behavior

Plugins, with Brainfuck and Bash as worked examples

Every stage of fcc is an extension behind a registry: inputs, outputs, hooks, and CLI commands. The stock compiler ships as default extensions; config disables, replaces, or installs them without touching code. src/ext/bf.v proves the seam composes — a whole language in ~100 lines that claims .bf files, transpiles to C, and reuses the frontend, both emitters and the object writer untouched. src/ext/bash.v goes one step further and parses a shell subset to C, so the binary runs with no shell involved:

$ fcc -c -o hello.o examples/hello.bf
$ gcc -o hello.exe hello.o
$ ./hello.exe
Hello World!
$ fcc -c -o hello.o examples/hello.sh
$ gcc -o hello.exe hello.o
$ ./hello.exe
hello world
count 1
count 2
count 3

No recompile is needed for the next language or command: any executable becomes an input plugin or a verb from config alone (fcc plugin add wlang -- wtrans --ext .w), and fcc plugin list shows everything registered, declared, or on PATH.

Details, the extension API, and the config/build files (fcc.toml, build.blip) live in docs/PLUGINS.md.

Design in one paragraph

The code generator sits behind a swappable backend interface. Phase 2 emits text assembly validated against three independent oracles; phase 3 assembles that text in-process to machine code (src/masm, byte-identical to GAS output) and writes COFF objects (src/coff). The front end is written once. Nothing is trusted without a cross-boundary test: a calling convention or data layout that is wrong in a way two fcc-compiled functions agree on is invisible to any test that never leaves the compiler.
